# matrix-appservice-nostr: design

Written to be read next to matrix-appservice-activitypub and matrix-appservice-atproto, whose room
model, command structure, storage rules and MSC4501 behaviour this bridge
copies. The command prefix is `[` (the siblings use `;` and `]`).

## Goal

Turn a Matrix homeserver into a Nostr server:

- Every local Matrix user can own one or more **Nostr IDs**. Each ID is its
  own Nostr identity: its own keypair (generated by the bridge, or the
  user's own imported key), its own NIP-05 handle on the homeserver's domain
  (`q@example.org`), and its own Profile Room. An ID defaults to the user's
  Matrix localpart but can be any free name.
- Users post, reply, react, repost, follow and DM across Nostr from ordinary
  Matrix rooms and clients.
- The bridge is itself a Nostr relay: the home relay for its users, where
  the rest of the network finds their posts and delivers replies, reactions
  and DMs to them.

## The storage rule

Same rule as the sibling bridges: **no event content or media is stored
outside Matrix.** Content and media live in Matrix rooms and the Matrix media
repository. The bridge's own database (SQLite or Postgres, same two backends
and migration tool as the siblings) holds only bookkeeping: IDs and keys,
follow relationships, the Nostr-event-to-Matrix-event map, a query index,
bans, and cursors.

A relay normally *is* a database of signed events, so this rule shapes the
whole design. A relay must hand out any event it accepted, byte for byte,
signature included, whenever a client asks. The bridge does that with
**two kinds of event source**, chosen by who signed the event.

### Events signed by a local key: rebuilt from Matrix

This is the atproto bridge's `record_sources` approach. When a Matrix
message becomes a Nostr event signed by a local ID, the bridge stores:

- the event's `id`, `pubkey`, `kind`, `created_at` and `sig` (64 bytes; a
  signature is bookkeeping, not content),
- the tags it needs to answer queries (see [the index](#the-relay-index)),
- a `source` recipe: a converter *kind* and *version*, the Matrix event ID,
  and any non-content inputs the converter needs, such as the Nostr ID of
  the post being replied to.

When the event is requested, the converter runs again against the Matrix
event fetched from the homeserver. Its output must hash to the stored `id`. The
stored `sig` is then attached and the event is served. As in
`matrix_records.py`, every converter is a frozen, versioned contract. It may
depend only on the Matrix event and state, never on the clock or config.
Changing how messages convert means adding `v2`, and `v1` events keep
rebuilding under `v1` rules for as long as they exist.

Rebuilding has the same three outcomes as in the atproto bridge:

| Outcome | Cause | What happens |
|---|---|---|
| Gone | The Matrix event was redacted | The index row is deleted, and a kind 5 deletion goes out if one hasn't already |
| Mismatch | Output hashes differently (a converter bug) | Not served; logged loudly |
| Unavailable | The homeserver is down or slow | Not served this time; **nothing is deleted** |

Nostr is simpler than ATProto here. There is no repository, Merkle tree or
commit chain, only standalone signed events.

### Events signed by someone else: embedded in the Matrix event

A remote user's event can't be rebuilt, because the bridge can't re-sign it.
So the **original signed JSON is carried inside the Matrix event that
represents it**, under a bridge-namespaced content key:

```json
{
  "msgtype": "m.text",
  "body": "gm nostr",
  "software.haven.nostr.event": { "id": "…", "pubkey": "…", "sig": "…", "kind": 1, "tags": [], "content": "gm nostr", "created_at": 1761000000 }
}
```

The same applies to an `m.reaction` that represents a kind 7, a DM message
that carries a gift wrap, and a Remote User Room state event that holds the
account's latest kind 0.

This keeps the content in Matrix, and it has useful side effects:

- Redaction is deletion. Redacting the Matrix event strips its content, so
  the relay stops serving the event. A Nostr kind 5 from the author becomes a
  redaction. A room moderator redacting a spam reply in Matrix also removes it
  from the relay.
- Nothing is duplicated. The Matrix event is both the display copy and the
  relay copy.

The source recipe for these rows is simply `{"kind": "embedded"}`. Serving
means fetching the Matrix event and returning the embedded object (after
checking its `id` against the index).

One limit: Matrix events are capped at 65,536 bytes. A remote event too
large to embed, typically long-form, can still be shown in Matrix, but the
relay doesn't serve it.

### The invariant

> The relay accepts and stores an event **if and only if** it has a home in
> Matrix.

`["OK", id, true]` is sent only after the Matrix event that holds it (or,
for a local event, the Matrix event it rebuilds from) exists. Anything the
bridge would not show in Matrix is rejected with `restricted:`, or is
processed without being stored (below). This is the rule that keeps the
relay from turning into a general-purpose store of strangers' content.

### Bookkeeping-only events ("inline")

As in the atproto bridge, a few event kinds have no Matrix content behind
them and *are* bookkeeping. Their tags are a list of references, and their
`content` is empty or bridge-generated:

| Kind | What | Built from |
|---|---|---|
| 3 | Follow list (NIP-02) | the `follows` table |
| 10000 | Mute list (NIP-51) | the `blocks` table |
| 10002 | Relay list (NIP-65) | config |
| 10050 | DM relay list (NIP-17) | config |

These may use the `inline` source, which stores the tags and `created_at`
directly. A kind 5 deletion is rebuilt from the Matrix redaction event, which
remains in the room after the redaction.

## Nostr IDs

This is the first of the three bridges where the external identity is
**chosen** rather than derived from the MXID, and where one Matrix user can
have **several**.

An ID is a NIP-05 name (`q`, shown as `q@example.org`). It comes with:

- its own keypair, so each ID is a separate Nostr identity with its own
  followers,
- its own Profile Room,
- its own follows, blocks and mutes (Nostr lists belong to a key).

### Rules for an ID's name

- Characters: `a-z 0-9 - _ .` (what NIP-05 allows), length between
  `bridge.id_min_length` and `bridge.id_max_length` (defaults 1 and 32).
- Unique across the bridge, and not on the reserved list (`admin`, `root`,
  `_`, `www`, the bot's localpart, and `bridge.reserved_ids`). This works like
  the atproto bridge's `HandlePolicy`.
- **Anti-impersonation**: a name equal to another existing local user's
  Matrix localpart is reserved for that user. `@bob` doesn't need to have
  created a profile for `bob` to be off-limits to everyone else.
- **Retired names**: a deleted ID's name is retired and isn't given to anyone
  else. Its old key is still out there, and clients that cached the handle
  shouldn't silently see it move to a stranger. Its owner can reclaim it.
- A Matrix user may hold up to `bridge.max_ids_per_user` IDs (default 5;
  bridge admins are exempt), which stops name squatting.

### Creating an ID

`[create profile` creates an ID named after the user's Matrix localpart.
This is the normal case and works like the siblings do now.

`[create profile <id>` creates an ID with any valid, free name.

**Localpart that isn't a valid ID.** Matrix localparts may contain `=`, `/`
and `+`, which NIP-05 doesn't allow. The same flow covers a localpart that
is already taken or reserved. In both cases `[create profile` doesn't fail
silently. The bot replies with a warning and two ways forward:

> ⚠️ `q+test` can't be used as a Nostr ID: Nostr IDs can only contain
> a–z, 0–9, `-`, `_` and `.`.
>
> 1. Use **`q-test`** instead: reply **confirm** to this message.
> 2. Or pick any ID you like: `[create profile <id>`

The suggestion swaps every invalid character for `-`, collapses repeats, and
trims separators off the ends. If the result is taken or reserved, it adds
`-2`, `-3`, and so on. Confirmation works the way the siblings' Danger Zone
does: the proposed name is carried on the warning message itself (in a
`software.haven.nostr.confirm` field), not in the database. A reply of
"confirm" re-checks that the name is still free and then creates the ID.

### Listing and switching

`[id` lists the user's IDs, numbered in creation order, as
matrix-appservice-activitypub's `;id` does:

```
Your Nostr identities:
1. q@example.org (active)
2. qbot@example.org
3. q-art@example.org
Switch with "[id <number|id>".
```

`[id 2` or `[id qbot` (or `[id qbot@example.org`) makes that ID
**active**. The numbers are positions in that list, so deleting an ID
renumbers the ones after it. `[id` always shows the current numbers.
(`[profiles` and `[switch` were the first names for these, and still work.)
`[status` shows the active ID too.

A user's first ID becomes active automatically. Deleting the active ID makes
the first remaining one active.

### Renaming an ID

`[rename <number or ID> <new name>` gives an ID a new name and keeps its
key. Nothing is lost: followers follow the key, so they stay, as do the
Profile Room, posts and DMs. The new name goes through the same checks as
creating an ID. The bot replies with what will change, and you reply
"confirm" (the same confirm-by-reply as the invalid-localpart flow):

> Rename **q-art@example.org** to **qart@example.org**? Your followers,
> posts and Profile Room stay; Nostr apps will show the new handle once
> they see your updated profile. Reply **confirm** to go ahead.

On confirm, the bridge:

- publishes a new kind 0 with the new `nip05`,
- keeps the **old name resolving to the same key** for
  `bridge.renamed_id_grace_days` (default 30), which NIP-05 allows: one key
  may have several names. Anyone who types the old handle during that time
  still finds the account,
- after that, retires the old name for its owner only, like a deleted one.
  It's never given to someone else, and the owner can take it back.

Renames are limited to one every `bridge.rename_cooldown_days` (default 7).
That stops an ID from cycling through names and reserving a pile of retired
ones.

### Which ID an action uses

1. **Inside one of your IDs' Profile Rooms** → that ID, always, whatever is
   active. This covers posting, replying and reacting there.
2. **Inside a DM room** → the ID the DM belongs to. A DM is between one of
   your IDs and one remote account, so sending from a different ID would
   break the conversation.
3. **Anywhere else** → your active ID. That includes reacting to or replying
   to a post in a Remote User Room or someone else's Profile Room,
   `[follow`, `[block`, `[repost`, and starting a new DM with `[dm`.

An undo uses whichever ID did the original. If you liked a post as `qbot`,
then switched to `q` and removed the reaction, `qbot`'s like is deleted. The
index row records which ID signed each event.

### Per ID vs. per Matrix user

| Thing | Belongs to |
|---|---|
| Keypair, NIP-05 name, Profile Room, kind 0 | the ID |
| Follows (kind 3), blocks and mutes (kind 10000), pins | the ID |
| DM rooms | the (ID, remote account) pair |
| Space | the Matrix user (holds every Profile Room of theirs) |
| Notifications room | the Matrix user. Once they have more than one ID, each notification names the ID it is for ("**qbot**: X liked your post") |
| Remote User Room membership | the Matrix user. One room per remote account, whichever of their IDs follow it |

**Leaving a Remote User Room** unfollows that account from every one of your
IDs that follows it, since the room is where its posts reach you. Joining a
Remote User Room or another local ID's Profile Room doesn't follow on its
own; `[follow` does, using the active ID.

## Keys

### Generated keys (default)

Creating an ID generates a secp256k1 keypair, creates the Profile Room, and
publishes a kind 0 (with `nip05`), kind 10002 and kind 10050.

The siblings store signing keys unencrypted in the database. This bridge
should go one step further: secret keys are encrypted at rest with a key
from the config file (`nostr.key_encryption_secret`). A copied database then
isn't a copy of everyone's Nostr identity. Nostr keys can't be rotated
without the identity changing, so leaking one is permanent.

### Bringing your own key

A Nostr key **is** the identity. Followers follow the pubkey, not the handle,
so someone with an existing Nostr following will want to bring their key.
`[create profile <id>` can create an ID from an existing key, and an existing
ID can have its key replaced. Three ways, in order of preference:

1. **Remote signing (NIP-46, "bunker").** The user connects a signer app
   (nsec.app, Amber, a hardware signer) with a `bunker://` URI or a
   `nostrconnect://` QR code. The bridge never sees the secret key. It asks
   the signer to sign each event, and to decrypt DMs (NIP-46 supports NIP-44
   decryption). The cost: posting and DMs stop working while the signer is
   offline, and events are queued and retried. The ID's `secret_key` is null
   and `bunker_uri` is set.
2. **Import through the widget.** The user pastes an `nsec` or a
   password-protected `ncryptsec` (NIP-49) into the bridge widget over HTTPS.
   The key goes straight to the bridge and is never in a room message. It is
   then held like a generated key.
3. **Never through a chat message.** A message in a room is stored by
   the homeserver unencrypted (the bridge doesn't do E2EE). So `[import key nsec1…`
   is refused with a pointer to the widget. If a user pastes an `nsec` into
   any bridged room anyway, the bridge redacts it and warns them.

NIP-26 delegation is deprecated and not supported.

When a key is imported, the bridge:

- points the ID's NIP-05 name at that pubkey (refusing if another local ID
  already uses that key),
- offers to import the account's existing follows (kind 3) and its recent
  posts into the Profile Room (posted by the bot with an MSC4144 per-message
  profile showing the ID, raw event embedded),
- publishes a kind 0 that adds `nip05` and otherwise keeps the existing
  profile fields.

**Replacing an ID's key after it has followers** loses those followers: they
follow the old pubkey. The bridge allows it (Danger Zone, confirmation-gated,
with a warning saying exactly that) but doesn't hide the cost.

**Export**: `[export key [id]` (Danger Zone) shows the `nsec`, or an
`ncryptsec` with a password, **in the widget only**, for the same reason.

### Events written by the user's other clients

An ID with an imported key may also post from Damus, Primal and so on. The
bridge picks those posts up two ways:

- A client that publishes to the bridge's relay is accepted (the author is
  local).
- The bridge also subscribes to the ID's pubkey on its NIP-65 write relays.

These posts are mirrored into that ID's Profile Room, sent by the bot with
an MSC4144 per-message profile, because an appservice can't send as a
non-ghost local user. The raw event is embedded in the message. Those rows
are `embedded`, not `rebuilt`, since the bridge didn't produce the bytes.

## NIP-05 handles (required)

Every ID has a NIP-05 handle. This is required by design, not optional.

- **Domain**: `bridge.domain`, required, as in both siblings, where it is
  also the domain handles live under. It doesn't have to be the homeserver's
  `server_name`. A host can put Nostr handles on any domain whose web server
  it controls, such as `q@example.org` for a homeserver at
  `matrix.example.org`, or `q@nostr.example.org`. It is separate from
  `nostr.relay_url`, which is where the relay itself lives.
- **Changing the domain later** is less painful than in the atproto bridge.
  Followers follow the key, not the handle, so on startup with a new
  `bridge.domain` the bridge republishes every ID's kind 0 with the new
  `nip05`, and nobody loses followers. Handles under the old domain stop
  resolving, though, unless that domain keeps proxying
  `/.well-known/nostr.json` to the bridge.
- **Endpoint**: the bridge serves `GET /.well-known/nostr.json?name=<id>`.
  The response includes only that name (never the full list) and
  `relays: {<pubkey>: [<nostr.relay_url>]}`. The bridge sets
  `Access-Control-Allow-Origin: *` itself, as the atproto bridge does for
  `/.well-known/`. A request without `?name` gets an empty `names`, and
  `_@domain` maps to the bot.
- **Reverse proxy**: the NIP-05 domain's web server must **proxy**
  `/.well-known/nostr.json` to the bridge. NIP-05 forbids redirects.
  `deploy/nginx.conf.example` will show the `location` block, which sits next
  to the existing Matrix `.well-known` ones. Unlike the atproto bridge, no
  wildcard DNS or wildcard certificate is needed.
- **Check**: at startup and in `[status`, the bridge fetches its own
  `https://<domain>/.well-known/nostr.json?name=_` and reports whether the
  proxy is set up. This plays the same role as the atproto bridge's
  `HandleRoutingProber`.

## The relay

### Endpoint

The relay's address is set by the host in `nostr.relay_url`, for example
`wss://nostr.example.org`. `deploy/nginx.conf.example` has a
server block for that hostname: TLS, WebSocket upgrade headers, and
`X-Forwarded-For`, which the rate limits need. The same hostname also
serves:

- the NIP-11 info document (`GET` with `Accept: application/nostr+json`):
  `limitation.restricted_writes: true`, `max_limit`, supported NIPs, the
  operator contact,
- media at `https://nostr.example.org/<sha256>.<ext>` (see [Media](#media)).

The protocol side covers NIP-01 `EVENT`/`REQ`/`CLOSE`/`COUNT`, live fan-out
to open subscriptions held in memory, and NIP-42 `AUTH`.

### What it accepts (writes)

| Event | Accepted from | Matrix home | Stored? |
|---|---|---|---|
| Any supported kind by a **local** ID's pubkey | Anyone (signature checked) | Profile Room message / reaction / redaction | Yes |
| kind 1 reply or mention that `p`-tags a local ID | Anyone, after [spam checks](#spam) | Threaded under the post (as a ghost), plus a notification | Yes |
| kind 7 reaction, kind 6/16 repost, kind 1 quote (`q` tag) of a local post | Anyone, after spam checks | `m.reaction` on the post / notification | Yes |
| kind 1059 gift wrap `p`-tagged to a local ID | Anyone (the outer key is throwaway) | Unwrapped into the DM room; the wrap is embedded in the message | Yes |
| kind 9735 zap receipt for a local ID | The ID's Lightning provider (checked against the `nostrPubkey` of the ID's `lud16`; only possible if one is set) | Notification | Yes |
| kind 5 deletion of an event stored here | Its author | Redaction | Rebuilt from the redaction |
| kind 3 follow list containing a local pubkey | Anyone | "X followed you" notification | **No.** Processed, then `OK false, "restricted: not stored"` |
| Anything else | | | **No.** `restricted: this relay only takes events for its own users` |

NIP-70 protected events (`["-"]` tag) are accepted only from a connection
authenticated (NIP-42) as their author.

### What it serves (reads)

| Events | Who can read them |
|---|---|
| Local IDs' public events, and the public replies/reactions to them | Anyone |
| Gift wraps | Only a connection authenticated (NIP-42) as the recipient |
| Remote User Room content (followed accounts' posts) | Nobody, by default. With `nostr.serve_followed_to_local_clients: true`, connections authenticated (NIP-42) as a local ID can read the posts of accounts **that ID** follows, so a user's own Nostr apps can show their timeline through the bridge |

**Serving followed accounts to local apps** is a host toggle, off by
default. It's fully supported when on: those posts already sit in Remote
User Rooms with their raw events embedded, and the index already covers
them. What it costs is homeserver load, because a timeline query from a phone
app can pull hundreds of events, each fetched from the homeserver (the in-memory
cache helps). When it's off, such a query just returns nothing for those
authors, and the app falls back to the accounts' own relays, as Nostr apps
do anyway.

### The relay index

`REQ` filters select by `ids`, `authors`, `kinds`, `since`/`until`, and
single-letter tags (`#e`, `#p`, ...). Matrix can't answer those, so the
bridge keeps an index. It holds references and timestamps only, never
`content`:

```
nostr_events(id PK, pubkey, kind, created_at, d_tag, room_id, matrix_event_id,
             source, sig, expires_at)
nostr_event_tags(event_id, letter, value)   -- only e, p, a, q, k, d
```

Serving a `REQ` means: query the index, apply `limit`, fetch each Matrix
event from the homeserver, rebuild or extract the Nostr event, check its `id`, and
send it. Fetched events go into an **in-memory** LRU cache keyed by Nostr ID,
which is cleared on restart and on redaction, so popular events don't hit
the homeserver every time. `max_limit` (NIP-11) caps how many events one `REQ` can
pull.

**Hashtags (`#t`) and full-text search (NIP-50) aren't supported.**
Hashtag values are words from a post's text, so indexing them would go
against the storage rule. This may be revisited later. What the relay does:

- A filter that has `#t` **and** something the index can narrow on
  (`authors`, `ids`, `#e`, `#p`) is answered properly. The candidates come
  from the index, and `#t` is checked on the rebuilt events in memory. That
  covers "this person's posts tagged #art", which is the common case.
- A filter that only `#t` could narrow (a network-wide hashtag search), or
  any filter with `search`, gets `["CLOSED", <sub id>, "error: hashtag and
  full-text search aren't supported by this relay"]`. NIP-01 says a relay
  that refuses a `REQ` must answer with `CLOSED`. `error:` is the closest of
  its standard prefixes, and clients treat it as "try another relay".
- NIP-11 leaves 50 out of `supported_nips`, so well-behaved clients won't
  send `search` here at all.

NIP-40 expiration: past `expires_at`, the event is no longer served. Whether
the Matrix event is also redacted is a config option, off by default.

## Spam

Nostr has no central moderation, so every relay that accepts writes from
strangers defends itself. The common pattern across relay software is the
same. The **khatru** framework's defaults rate-limit events, `REQ`s and
connections per IP, and reject base64-embedded media. **nostrify** (Ditto's
library) ships policies for duplicate content, "hellthreads" (events tagging
dozens of people), proof-of-work, size limits, banned pubkeys, keyword and
regex filters, and web-of-trust. strfry runs write-policy plugins for the
same jobs. Other relays get the same effect from whitelists, payment or
web-of-trust.

This relay is in a better position than most. It only accepts strangers'
events that are *addressed to a local ID* (see the write table above), so a
flood can only arrive as replies, mentions, reactions or DMs aimed at
the server's own users. The defences are layered, cheapest first. All of them
also apply to events the bridge pulls in through its `#p` subscriptions on
public relays, not just to writes made directly to the relay.

### 1. Rate limits (token buckets)

Per IP (behind the proxy, from `X-Forwarded-For`), with defaults taken from
khatru's sane defaults:

| Limit | Default |
|---|---|
| New connections | burst 100, refill 1 per 5 min |
| `REQ`s | burst 100, refill 20 per min |
| `EVENT`s from non-local authors | burst 10, refill 2 per 3 min |

Per pubkey, for non-local authors: events aimed at local IDs, burst 10,
refill 5 per hour. A further per-(pubkey, local ID) limit stops one account
spamming one person.

Local IDs (authenticated with NIP-42, or simply signed by a local key) are
exempt from the event limits. The bridge's own outgoing connections are
never limited.

Over the limit → `OK false, "rate-limited: …"` or `CLOSED "rate-limited: …"`.

### 2. Cheap content checks

Applied to every event from a non-local author:

- **Size**: over `nostr.max_event_bytes` (default 64 KB, which is also what
  fits in a Matrix event) → rejected.
- **Timestamps**: more than 15 minutes in the future, or (for replies and
  reactions, not backfill) more than a few days old → rejected.
- **Hellthread**: more than `nostr.max_p_tags` (default 20) `p` tags →
  rejected. Mass-mentions are the most common Nostr spam pattern.
- **Base64-embedded media** in `content` → rejected.
- **Duplicates**: the same content from several pubkeys within a short window
  is a classic bot wave. A hash of the content, kept **in memory only** and
  forgotten after the window, catches it. Nothing is stored.
- **Keyword/regex lists** (`nostr.spam_patterns`), empty by default, for
  operators who want them.

### 3. Trust tiers

Every non-local pubkey falls into one of three tiers:

| Tier | Who | Treatment |
|---|---|---|
| Trusted | Followed by any local ID, or one a local ID has replied to or DMed | No PoW, generous limits |
| Web of trust | Followed by someone a local ID follows (two hops) | Normal limits |
| Stranger | Everyone else | Normal limits, and PoW or refusal during a wave (below) |

The two-hop set is built from the follow lists of accounts local IDs follow,
which the bridge fetches anyway. It is held in memory and rebuilt
periodically. It's a set of pubkeys only, nothing more.

`nostr.inbound_policy` sets how strangers are treated normally:

- `open`: accepted within the limits. This is the **default**, so new users
  can be found by people who don't know them yet.
- `pow`: NIP-13 proof-of-work of at least `nostr.stranger_pow_bits` (default
  20). Rejections say `pow: …`, which capable clients answer by mining and
  resending.
- `web_of_trust`: strangers are refused.

### 4. Automatic bans (strikes)

Each rejection for rate limits, duplicates, hellthreads, bad timestamps,
spam patterns or invalid signatures is a **strike** against both the pubkey
and the IP. Strikes are counted in memory over a sliding window. Crossing
`nostr.strikes_to_ban` (default 10 in 10 minutes) bans that pubkey and IP:

- 1 hour the first time, 24 hours the second, 7 days after that (escalation
  remembered for 30 days),
- a banned pubkey gets `blocked: …`, and a banned IP is disconnected and
  refused at connect,
- bans are stored in a `bans` table (pubkey or IP, until, reason, strike
  count): bookkeeping.

Matrix users feed the same system:

- A local user or room moderator **redacting a ghost's reply** in their
  Profile Room or thread is one strike against that pubkey.
- A **Matrix report** (`/report`) of a ghost's event is three strikes, and
  bridge admins are notified.

Admins can act directly:

- `[ban <npub|nip05|IP> [duration] [reason]` bans manually.
- `[ban … purge` also redacts everything that pubkey has in bridge rooms,
  which removes it from the relay too, because redaction is deletion.
- `[unban …` lifts a ban, and `[bans` lists them.

### 5. Wave detection ("shields up")

Bot waves usually show up as many **never-seen pubkeys** acting within a few
minutes. The relay counts distinct stranger pubkeys whose events pass
checks 1 and 2. Above `nostr.wave_threshold` (default 30 within 5 minutes),
it switches automatically to the stricter of `pow` or the configured
`nostr.wave_policy` (default `pow`) for strangers. It then tells bridge admins
in their bot DM ("🛡️ Shields up: 47 new accounts in 5 minutes; strangers now
need PoW"). After `nostr.wave_cooldown` (default 1 hour) without crossing
the threshold again, it goes back and says so. Trusted and web-of-trust
pubkeys are never affected.

### 6. DMs

A gift wrap's outer pubkey is throwaway, so per-pubkey limits can't see the
sender until it is unwrapped. Wraps are limited per IP and per recipient.
Once unwrapped, the real sender goes through the same tiers and bans. A DM
from a stranger arrives as an **invite** to a new DM room. Declining it is a "no", and nothing appears in the user's room
list until they accept.

## Getting posts from followed accounts

Nostr has no inbox and no firehose. The bridge is a client that goes and
gets things, much like the atproto bridge's Jetstream plus catch-up loop.

- **Relay lists**: for each followed pubkey, the bridge fetches its kind
  10002 from `nostr.discovery_relays` (indexer relays such as
  `purplepag.es`) and caches the URLs (bookkeeping).
- **Subscriptions**: it groups followed pubkeys by write relay and keeps one
  connection per relay with `REQ {authors: [...], kinds: [0,1,5,6,7,16,...],
  since: <cursor>}`. Accounts without a relay list go to
  `nostr.fallback_relays`.
- **Cursors**: for each relay, `created_at` of the newest event seen is saved.
  After downtime, the subscription restarts from there minus a safety
  window. Replays are harmless because events are deduplicated by `id`.
- **Inbound for local IDs**: the bridge also subscribes to `#p: [local
  pubkeys]` on `nostr.publish_relays`. Many clients still send replies to big
  relays rather than to the recipient's inbox, and this catches them. Those
  events go through the same acceptance and spam rules as writes to the relay.
- **Mirroring**: as the atproto bridge does it. A post becomes one message
  from the ghost, and its first image or video is copied into Matrix. A reply
  to a post that is in Matrix is threaded under it and cross-posted with a
  "⤵️ Reply to" line. A reply to a post that isn't in Matrix pulls in the
  conversation first. Reposts and quotes follow the atproto bridge, including
  `quote_import_policy`. Every mirrored event embeds its raw JSON.

## Publishing

When an ID does something, the bridge signs it, adds it to the index (so
its own relay has it), and sends it to:

- `nostr.publish_relays`: a few large public relays, for reach, since many
  clients only read the relays they are configured with,
- for replies, mentions, reactions and reposts: the read (inbox) relays from
  the target's NIP-65 list,
- for DMs: only the recipient's kind 10050 relays (NIP-17).

Each ID's kind 10002 lists `nostr.relay_url` as both read and write, plus
`publish_relays` as write.

## Rooms

These are the same room types as the siblings.

- **Profile Room**: one per ID. Messages become kind 1 notes signed by that
  ID. The room's name, topic and avatar are the kind 0 `name`/`about`/
  `picture`. Pinning maps to a NIP-51 pin list (kind 10001). MSC4501 profile
  room type, as in the siblings.
- **Remote User Room**: one shared room per followed Nostr pubkey, joined by
  its ghost and every local follower. The latest kind 0 is kept as
  `software.haven.nostr.profile` state, embedded raw.
- **DM room**: one per (local ID, remote pubkey), carrying NIP-17 private
  DMs. Room name shows which ID it's from when the user has more than one.
- **Notifications room**: one per Matrix user (see above).
- **Space**: one per Matrix user, holding all of the above.

**Ghost users** are `@nostr_<hex pubkey>:server`. The hex form is valid as
a localpart and never changes, whereas NIP-05 names can. Display name, avatar
and banner come from kind 0. With `msc4503_external_handle` the ghost records
its NIP-05 handle, or its `npub` when it has none.

## Mapping Matrix actions to Nostr

The ID used for each action follows [Which ID an action uses](#which-id-an-action-uses).

| Matrix | Nostr |
|---|---|
| Text message in a Profile Room | kind 1. No length limit, so no splitting into threads |
| Image/video/file in a Profile Room | kind 1 with the media URL in `content` and an `imeta` tag (NIP-92: `url`, `m`, `x` sha256, `dim`, `blurhash`); caption is the text |
| Reply (rich reply or thread) to a post | kind 1 with NIP-10 marked `e` tags (`root`, `reply`) and `p` tags |
| Pill of a ghost or local user | `nostr:npub…` in `content` plus a `p` tag (NIP-27). A local user's pill uses their active ID |
| Link to a Nostr post (`nevent`/`note`, njump/primal URL) | quote: `nostr:nevent…` plus a `q` tag (NIP-18) |
| Reaction 👍 | kind 7 `"+"` |
| Any other emoji reaction | kind 7 with that emoji. Nostr allows any, unlike Bluesky |
| Custom emoji reaction (MSC4027 shortcode) | kind 7 `:shortcode:` plus an `emoji` tag (NIP-30), reusing the AP bridge's custom emoji handling |
| Reaction 🔁 | kind 6 repost (kind 16 for non-kind-1 targets) |
| Redaction | kind 5 deletion (NIP-09), signed by the ID that made the original |
| Edit (`m.replace`) of a published note or comment | Nostr notes are immutable: a kind 5 deletion of the old note, then a new note or comment from the edit's `m.new_content`, answering what the original answered. The new note's recipe names the edit (`edit`), so it rebuilds from the edit event; it keeps the original Matrix event, so later edits and redactions find it. |
| Spoiler (`data-mx-spoiler`) | `content-warning` tag (NIP-36) |
| Profile Room name/topic/avatar/banner | kind 0 `name`/`about`/`picture`/`banner`, plus `nip05` |
| Pin | kind 10001 pin list (NIP-51) |
| `[follow` / `[unfollow` / leaving the room | that ID's kind 3 updated |
| `[block` | that ID's kind 10000 mute list (public entries) |
| Message in DM room | NIP-17: kind 14 rumor, sealed (13) and gift-wrapped (1059) with NIP-44, sent to the recipient and to the sender's own copy |

Incoming, it's the reverse. A `"+"` reaction shows as 👍, a `"-"` (dislike)
is ignored, a kind 9735 zap receipt is a notification ("⚡ X zapped your post
1,000 sats"), and NIP-04 legacy DMs are received and shown but never sent.

Not supported: sending zaps (needs a Lightning wallet, NIP-47/57),
communities (NIP-72) and groups (NIP-29). Long-form
articles (kind 30023) are shown as a title, summary and link; polls (NIP-88)
work both ways.

## Media

Media follows the storage rule. Bytes live only in the Matrix media
repository.

- **Outbound**: Nostr posts carry plain URLs, so local media must be publicly
  fetchable. The bridge serves `https://nostr.example.org/<sha256>.<ext>`,
  which is the **Blossom** (BUD-01) URL shape. The `blobs` table maps sha256
  to mxc, and requests are proxied from the media repo with the appservice
  token (authenticated media), as the siblings' `/media/` routes do. Images
  are EXIF-stripped and re-encoded when needed, and the re-encoded file is
  uploaded back into Matrix, as in the atproto bridge's `media.py`. That keeps
  the bytes in Matrix, and the sha256 never changes.
- **Inbound**: images and video are copied into Matrix (size cap
  `nostr.max_media_mb`). The raw event keeps the original URLs.
- **Uploads from users' other Nostr apps** (imported-key IDs): BUD-02
  `PUT /upload` with a kind 24242 auth event signed by a local key. The file
  goes into the Matrix media repo, and the server returns a descriptor.

## Posting and media in detail

The details of posting and media, which the sections above leave open.

### Outbound: a Matrix message becomes a kind 1

**Text.** Built from `body`, never `formatted_body`, with the rich-reply
fallback stripped (as in `matrix_records.message_body`). The HTML is only
used to find **pills** and links, so a pill's display text in `body` is
replaced with `nostr:npub…` (NIP-27) plus a `p` tag. A pill of a local Matrix
user uses their active ID **at the time of posting**. That ID's pubkey goes
into the source recipe, since the converter can't look up "active" again
later. A pill of a user with no ID stays plain text.

**`created_at`** is `origin_server_ts` divided by 1000, rounded down.

**Media.** The post's `content` is the caption, then a newline, then the
media URL. An `imeta` tag carries `url`, `m`, `x`, `size`, `dim` and
`blurhash`. Every file type is posted this way: Nostr has no separate "link
card" form, and clients show images, video and audio inline from `imeta`.
Images are EXIF-stripped and re-encoded when needed, exactly as in the atproto
bridge. One Matrix message is one file, so a post has at most one attachment.

**Frozen inputs.** The converter may not read config, but the media URL
contains the media host, and a host can change its domain. So the
**media URL base** (e.g. `https://nostr.example.org`) and the sha256 go into
the recipe when the event is created. Old events keep rebuilding with the old
URL. That URL breaks if the old host stops serving, but the event's id never
changes. A changed host is also why the bridge publishes a **BUD-03 server
list (kind 10063)** for each ID: clients that understand Blossom can then find
a blob by its hash on the new host.

**Profile.** A kind 0 is rebuilt from the Profile Room's `m.room.name`,
`m.room.topic`, `m.room.avatar` and banner **state event IDs**. Old state
events can still be fetched after newer ones replace them. The recipe also
stores the `nip05` string, since renames and domain changes alter it.
`picture`/`banner` are media URLs as above. Any change to those state events
or to the handle publishes a new kind 0.

### Inbound: a Nostr post becomes a Matrix message

**Kinds mirrored**: 1 (notes), 6/16 (reposts), and also the media-first
kinds many newer clients post: **20** (NIP-68 pictures, e.g. Olas), **21/22**
(NIP-71 videos), and **1111** (NIP-22 comments) when it replies to something
in Matrix. Without 20–22, "media both ways" misses a large share of media
posts.

**Text rendering.** Kind 1 content is plain text. Some clients write
markdown, but it isn't standard, so it isn't rendered. The bridge:

- links URLs,
- turns `nostr:npub`/`nprofile` into a pill if the bridge has a ghost or
  local ID for that key, and otherwise into a link,
- turns `nostr:note`/`nevent`/`naddr` into a `matrix.to` link if that event
  is in Matrix, and otherwise into a link to `nostr.web_viewer_url`
  (default `https://ditto.pub/`),
- shows hashtags as text,
- shows NIP-30 `:shortcode:` custom emoji as inline images, copied into
  Matrix, reusing the AP bridge's custom emoji handling,
- turns a `content-warning` tag into a spoiler.

**Media.** Found from `imeta` tags, and for posts without them, from URLs in
the text that end in a media extension. As in the atproto bridge, the first
image or video becomes the Matrix message, captioned with the text (minus
that URL). Further attachments are listed under "Other Attachments:" as
links. Over `nostr.max_media_mb`, nothing is copied and the media is just
linked. When `imeta` has an `x` hash, the download must match it. If the URL
is dead, the bridge tries the author's kind 10063 Blossom servers with that
hash before giving up.

**Fetching safely.** Every inbound media URL, custom emoji, avatar and remote
NIP-05 lookup is a URL a stranger chose. Fetches go through one guarded client
that:

- refuses private, loopback and link-local addresses, checked after DNS
  resolution and again on every redirect (the atproto bridge's
  `identity.py` already does this, and can be reused),
- caps response size and time,
- never sends the bridge's credentials.

**Ghost profiles.** From the account's latest kind 0: display name (falling
back to `name`, then a shortened `npub`), avatar and banner copied into
Matrix. The `nip05` is **shown only after verifying it**, as NIP-05 requires:
the bridge fetches the handle and checks that it points back to the same key,
and re-checks when the kind 0 changes. An unverified handle is not displayed.

**Timing.** Mirrored posts carry the event's `created_at` as their Matrix
timestamp (the appservice `ts` parameter), as the siblings do.

### Following: what `[follow` accepts

`npub1…`, `nprofile1…` (whose relay hints are used first), a 64-character hex
key, a NIP-05 handle (`name@domain`, or just `domain` for `_@domain`), and
web links of the form `njump.me/<npub|nprofile>` and
`primal.net/p/<npub>`. Following an account backfills its latest
`nostr.backfill_on_follow` posts (default 20), and `[backfill [N]` gets more.

### Talking to other relays

- **One connection per relay**, shared by all subscriptions and publishes,
  reconnecting with backoff. Each relay's NIP-11 limits (max subscriptions,
  max filters, max message size) are read and respected.
- **NIP-42 auth outbound.** Some relays, especially inbox and DM relays,
  require auth before they take writes. The bridge answers `AUTH` challenges
  as the ID whose event it is sending, so it may need one authenticated
  connection per ID per such relay.
- **Being rate-limited ourselves.** Public relays limit by IP, and every
  local ID publishes from the bridge's one IP. So each relay gets one outgoing
  queue that paces sends and backs off on `rate-limited:`. The relays in
  `publish_relays` should be ones that tolerate a server publishing on behalf
  of many users. That's a deployment note for INSTALL.md.
- **Echoes.** Events the bridge published come back through its own
  subscriptions. Every incoming event is checked against the index by `id`
  first, so an echo is dropped before any work is done.

### Telling the user whether it worked

A post is **published** once the bridge's own relay has it, and the bridge's
own relay always takes it. That makes the post visible to anyone who looks up
the ID's handle. Public relays are then tried in the background:

- If **none** of `publish_relays` accepts the event after retries, the bot
  replies in the Profile Room: "Couldn't reach any public Nostr relay, so
  this post can only be seen by people who look you up directly. It'll keep
  retrying." (Same wording style as the atproto bridge's "Couldn't publish
  that to Bluesky.")
- Rejections that won't change on retry (`blocked:`, `invalid:`) are
  reported with the relay's own reason.
- A relay that refuses an ID by policy (`restricted:`/`blocked:`, e.g. a
  web-of-trust relay the ID isn't trusted by yet) is marked as refusing that
  ID and skipped for `nostr.refused_relay_retry_hours` (default 24). It isn't
  hit again on every post. If it's the only relay that refused, the user is
  told once, not per post.
- Anything not yet delivered is kept in `pending_publishes` (ids and recipes
  only) and retried after a restart.

### Profile Rooms: who posts

As in the atproto bridge, only the owner's messages publish as the ID.
Messages from anyone else in the Profile Room aren't published, unless they
reply to a post, which publishes a reply from *their* acting ID. An edit
republishes the note it edits, as the identity that published it. When creating an ID, the bot reminds the user that everything
posted in the Profile Room is public on Nostr, even if the Matrix room is
private.

### Who can have IDs

Any local user of the homeserver (`homeserver.server_name`). Users on other
Matrix servers can't, which is the same as the siblings.
`bridge.id_allowed_users` (a list of MXID globs, empty means everyone local)
lets a host restrict it.

### Testing

Every converter version has golden tests: fixtures of Matrix events with the
exact Nostr event id they must produce. A fixture is never edited once its
version ships (a changed converter would make every event it built
unservable); a new version adds new fixtures.

## Games: webxdc mini apps (NIP-DC)

Off unless `webxdc.enabled`. Bot-refereed games (chess, Connect 4, cards on
poster.place) need nothing of their own: they are ordinary posts, replies and
DMs with a bot, and work through the bridge like any other.

**The protocol** is Ditto's NIP-DC draft, which poster.place implements too,
so a game is playable from any of them:

- **The game** is a post with a `.xdc` file (a zipped web app): an `imeta`
  tag with `m application/x-webxdc`, `url`, `x` and a `webxdc` identifier,
  random per post. The identifier, not the event, is the game: a repost is
  the same game, the same file posted again a new one.
- **A move** (`sendUpdate()`) is a kind 4932 event, signed by the player,
  with the identifier in an `i` tag, the payload as its content and an `alt`.
  Serials are assigned locally, by `(created_at, id)`.
- **Realtime** (`joinRealtimeChannel()`) is kind 20932: ephemeral, signed by
  a key made per session (never the player's), base64 content, `i` tag.

**Game posts in Matrix.** A game post shows where any post would (its
author's room, a Profile Room, a thread) as text plus "🎮 *name*: reply
`[play` to open". The `.xdc` is not copied into Matrix: players' browsers
fetch it from where it was posted, and check `x` when it is a hash. A `.xdc`
uploaded to a Profile Room is published as a game post (note v4, which adds
the `webxdc` identifier to the `imeta`), served from the Matrix media
repository like any upload.

**Moves live in Matrix**, by the storage rule: each 4932 is a hidden event
(`software.haven.nostr.webxdc.update`, carrying the signed event) in a thread
under the game post, in the post's home room, sent by the player's ghost (or
the bot, for a local player). Clients don't display custom event types, so the
thread stays readable as the place to talk about the game. The relay indexes
`i` tags, serves moves to Nostr apps, and accepts 4932 and 20932 only for
games that have a post here. While a game has been opened in the last
`webxdc.active_days`, the bridge subscribes to its `#i` on the game author's
relays and the fallbacks.

**Playing.** `[play`, sent as a reply to a game post in any room, opens it in
the user's **Games room**: a room per Matrix user, made on first use, filed in
their space, re-invited if left. The bot sets that room's widget to the game,
replacing the previous one (state lives on Nostr, so nothing is lost but a
live realtime session), centred with `io.element.widgets.layout`. The first
time, the bot explains that games need a client with widgets (Element Web or
Desktop). Moves are signed as the user's Active identity; realtime packets go
only to the bridge's relay and the game author's relays.

**The player** is the widget page on the bridge's origin, signed in with the
client's Matrix OpenID token like the bridge widget, talking to the bridge
over a websocket for moves and realtime. It downloads and unzips the `.xdc`
and runs it in a frame on the **sandbox origin** `webxdc.sandbox_domain`
(`xdc.<domain>`): a separate origin, so an app can't reach the bridge's or the
homeserver's storage. That origin serves only a loader and a service worker
(from poster.place, GPLv3 like this bridge); every file an app asks for
comes back over `postMessage` from the player, and its CSP names no host, so
an app has no network access at all. All apps share that one origin, so one
app can read another's saved data, never the user's keys or session. An app
origin per game would need a certificate for `*.xdc.<domain>`.

| Setting | Default | |
|---|---|---|
| `webxdc.enabled` | `false` | games on or off |
| `webxdc.sandbox_domain` | `xdc.` + `bridge.domain` | the sandbox origin |
| `webxdc.active_days` | `14` | how long after a game was last opened its moves are followed |
| `webxdc.max_update_kb` | `128` | largest move accepted |

## The Nostr Games widget

`bridge.games_hub` serves `/xdc/hub` (widget id `nostr-games`) and its API,
all behind a widget session. Games rooms get it when made. The layout
(`io.element.widgets.layout`) puts the game widget in the centre and the
hub on top, or the hub in the centre when no game is open.

- **Catalog**: `{"kinds":[1063],"#m":[the three webxdc types]}` and
  `{"kinds":[1,1068,1111,1621],"#t":["webxdc"]}` (poster.place's two
  queries), from `webxdc.catalog_relays` and `nostr.publish_relays`, plus
  the bridge's own index. Verified; per game id, the oldest announcement
  wins (a later picture is borrowed). Kept in memory for 15 minutes,
  never stored. Opening one imports its post as `[import` does.
- **A room's games**: the pinned events, widget state with `data.game`,
  and the last 1,000 timeline events, read by the bot. A game is anything
  with `software.haven.nostr.webxdc` (mirrored posts and cards carry it)
  or an `.xdc` file.
- **A room's own games**: an `.xdc` file in Matrix gets the id
  `uuid5(URL, "matrix:<room>/<event>")` and a `webxdc:local:<id>` entry
  (room, event, mxc). Only the room's members may load or play it. Moves
  are `software.haven.nostr.webxdc.update` events in a thread under the
  file, holding an unsigned update (`id`, `created_at`, `content`, tags)
  that is never published; realtime stays among the players here.
- **Opening** (from the hub or a card's 🎮) needs the right to change the
  room's widgets. The bot sets the widget and posts the card.

## Communities: Concord

Concord (github.com/concord-protocol/concord, CORD-01..08) is a community
protocol over Nostr: a community is a shared key (holding it is
membership), an owner-rooted signed roster, and relays that carry only
encrypted streams of kind 1059 events. `bridge.concord` implements the parts
a member needs:

- **Invites** (CORD-05): the link's naddr locates a kind 33301 bundle, its
  fragment carries bootstrap relays and a token whose HKDF decrypts the
  bundle. The owner commitment (`community_id`) is checked before anything
  is trusted.
- **The Control Plane** (CORD-02/04) is read for the community's metadata and
  channels, taking the highest version of each entity signed by the owner
  or by a member the owner granted a role. Legacy (pre-split) communities
  are read at their community-root address.
- **Channels** (CORD-03): each readable channel is a room in the community's
  Space. Chat rumors (kinds 9, 1111, 7, 5, 3302) are opened, their authors'
  seals and channel tags checked, and shown by the authors' ghosts; members
  here post the same shapes, sealed and signed with their identity's key and
  wrapped with the channel key. Attachments use AES-GCM with the key in the
  `imeta`, both ways.
- **Storage.** A community's keys and channel map are one vault-encrypted
  bridge_state entry; rumor ids and Matrix events map to each other in
  bridge_state. Messages live in Matrix, as plain text: the rooms can't be
  encrypted by the bridge, and `[join` warns of it.
- **Planes.** Each community is followed at every address it uses: the
  Control Plane, the Guestbook, each readable channel, and the next
  epoch's rekey addresses (the base one, and one per channel).
  `addresses()` maps an incoming wrap's author to its community and plane.
- **The roster** (CORD-04) is folded outward from the owner until it
  settles: roles (position, permissions), grants and the banlist (at its
  one coordinate), each honoured only from someone allowed to set it.
  Roles show as power levels (90/75/50), for display only.
- **The Guestbook**: joins and leaves, latest per member, give `present`,
  and ghosts join or leave the rooms. Kicks count only from someone with
  KICK who outranks the target. A kick read from history only updates
  `present` (a rejoin follows an old kick). A live one removes a member
  here.
- **Rekeys** (CORD-06): a 3303 at a rekey address is accepted only from
  BAN (base) or MANAGE_CHANNELS (channel) holders, at the next epoch, with
  `prevcommit` matching the key held (the root, for a public channel). Our
  members' locators find their blob; its scope and epoch are checked
  before the key is adopted. If all chunks are in and none is ours, that's
  a removal. After a move, `catch_up` follows further rotations, then the
  Control Plane and Guestbook are read again.
- **Disappearing messages** (CORD-08): rumors past their `expiration` are
  refused. Others get a `concord:exp:<ts>:<event>` entry, and
  `expiry_loop` redacts them when due. Outgoing rumors carry the folded
  timer. A 1740 notice is shown only from MANAGE_METADATA holders.
- **Later:** moderation from Matrix, channel-scoped roles, voice (CORD-07).

## Groups: NIP-29

`bridge.groups` joins relay-based groups. A group is (relay, id); its
relay signs the metadata, admin and member lists (39000-39002) with its
NIP-11 `self` key. Without one, the first signer seen is trusted (some
relays omit `self`; NIP-11 `pubkey` is the operator's and may differ).

- **Joining** sends a 9021 (with the invite `code`) unless the newest
  9000/9001, or the 39002 list, already has the identity. `duplicate:` is
  success. A refusal from a closed group without a code stops. Any other
  refusal leaves the request pending, and a later 9000 says so in the room.
- **Rooms**: one Space per relay (`nip29:space:<relay>`), one room per
  group (`nip29:room:<room>` → `relay'id`). Settings and member IDs live in
  `nip29:g:<relay'id>`; message mappings in `nip29:m:`/`nip29:x:`, as for
  Concord. Nothing of the messages themselves is stored.
- **Subscriptions** (`groups.desired`) are per relay and per reading
  identity. The filter's `_auth` makes `feeds` subscribe with that
  `auth_pubkey`, so members-only relays get NIP-42 AUTH as a member.
- **Outgoing** events carry `h` and up to three `previous` references
  (first 8 hex characters of recent events by others, kept in memory).
  The mapping is recorded before publishing, so the relay's echo isn't
  shown twice. A relay refusal is told in the room, as a reply.
- **Moderation** kinds (9000, 9001, 9005) count only from listed admins or
  the relay key; the relay is the real enforcer.

| `processed_events` | Matrix event IDs already handled, kept 7 days. Deduplicated by event ID, not transaction ID as the siblings do: Synapse on SQLite restarts transaction numbering after a restart, and a reused ID would otherwise drop new events |
| `bridge_state` | as in the siblings |

Strike counters, rate-limit buckets, the duplicate-content window, the
web-of-trust set and the event cache are all **in memory**. Only bans
survive a restart.

## Running next to the siblings

- One process, FastAPI plus uvicorn, Python. Talks to the homeserver only
  through the Client-Server API and the appservice push API, never its
  database, so it works with **any spec-compliant homeserver**, not just
  Synapse. The config section is `homeserver:` (`base_url`, `server_name`).
- The **Synapse Admin API** is used for one thing only: counting Synapse
  server admins as bridge admins. It's behind
  `bridge.use_synapse_admin_api`, named as in matrix-appservice-activitypub.
  It is **off by default**, because nothing else needs it and
  `bridge.admins` covers the same ground on every homeserver. With it on,
  `homeserver.synapse_admin_token` is required. Nothing else in the bridge
  may call a Synapse-only endpoint. A future feature that genuinely needs one
  goes behind the same switch and must still work, in a reduced form, with
  it off.
- Its own appservice registration, bot, and ghost namespace (`nostr_`, next
  to `ap_` and `at_`), so all three bridges can run on one homeserver.
- Same widget, Danger Zone confirm-by-reply pattern, MSC4501 settings,
  space and notifications room layout, and docs set (`README`, `FEATURES`,
  `COMMANDS`, `CONFIG`, `INSTALL`). The widget gets an ID switcher.
- Crypto: BIP340 Schnorr signatures are implemented in pure Python
  (`bridge/nostr/secp256k1.py`, checked against the BIP340 test vectors),
  because `coincurve` has no build for Python 3.14, which the siblings run
  on. coincurve is used automatically when installed, and is much faster.
  Pure Python is about 3.7 ms to sign and 2.6 ms to verify, so a few hundred
  verifications a second per core, enough with the relay's rate limits.
  `cryptography` covers the key vault (AES-GCM, HKDF), NIP-44 (ChaCha20,
  HKDF, HMAC) and NIP-49 (scrypt; XChaCha20 via HChaCha20). Bech32 (NIP-19)
  is vendored.
